## 4. 画布重新挂载会吞掉没保存的输入 —— **已修（2026-09-27，提交 `c65959e`）**

这一节原来是"登记问题"，结论是"会丢、但触发面窄，先登记，动手前再定修法"。现在它是一条
已修的记录：**哪几条路真的能走到、每条路的处置、以及为什么这么修**。原文的判断里有一条
是错的（4.2），**留着它**——它是个好反例：一句没实测过的因果链写进文档之后，读起来和
实测过的一模一样。

### 4.1 挂载点在哪（核对过，但原文漏了最要紧的一条）

- 根布局是稳定的：`src/app/layout.tsx` 里 `AuthProvider` / `DemoProvider` / `AppShell`
  挂在模块层，路由之间不会重挂。
- `AppShell.tsx` 在 `!ready` 时返回启动屏并**不渲染 `{children}`** —— 所以页面内容是
  "从无到有"挂载一次。但 `ready` 只跟登录态恢复有关，**不受计划加载影响**。
- 原文记的是 `Workbench.tsx` 的 `<PathView key={spaceId} />`：`spaceId` 在 `growth.goalId`
  变化时同步，首次拿到计划时从 `'goal'` 变成真实 UUID → key 变化 → 整棵 PathView 子树
  （含 ReactFlow 画布）卸载重建。这一条本身没错（它就是 `docs/08-DEPLOYMENT.md` 第四节
  记的"计划到达时整页重新挂载一次"，严格说不是整页，是**画布子树**）。

  **漏掉的是更常见的那一条：四个视图是一个三元表达式，点一下页签整棵画布子树就卸载。**
  它和 key 无关、每次切视图都发生，而且带走的正是同样的两样东西（ReactFlow 内部的视口、
  弹窗里那一组 `useState`）。所以"触发面很窄"这个前提本身就是错的。

### 4.2 什么情况会再次触发（**原文这一条错了**）

原文写的是：读计划失败时 `setPlan(null)`，`growth` 退回空树、`goalId` 回到 `'goal'`，
下一次读成功又变回 UUID → **再重挂载一次**；所以"后端抖一下，用户就会看到他正在编辑的
东西消失"。

**按今天的代码走不到。** 计划那次读取挂在 `useEffect(..., [isReal, space.id])` 上，
只在换空间 / 整页加载时跑；失败之后只置 `planError`，**没有任何重试入口**能制造出
"下一次读成功"。修这个问题之前的实测（4.5）也没有复现出它。它是一句按代码推出来的
因果链，写法上却是断言 —— 这就是它被留在文档里当反例的理由。

实测出来的触发面是这四条（前两条是缺陷，后两条是设计，都要留着）：

| 触发 | 后果 | 处置 |
| --- | --- | --- |
| 点一下视图页签（**每次**） | 画布子树卸载 → 视口重置、弹窗与没提交的输入消失 | 修 |
| 离开工作台再回来（后退/前进、从"全部空间"再进） | 同上；且这一层连 Provider 一起重挂 | 修 |
| 计划第一次到达（`'goal'` → 真实 UUID） | 画布子树重建一次 | 留着：那一刻还没有东西可丢（"新建节点"由 `planLoading` 挡着），而且它本来就是"从占位树换成真树" |
| 双击进入子空间 / 换空间 | 整棵子树重建 | **留着**：换一层就该换一份状态，`key` 就是干这个的 |

**还有一条实测出来、和直觉不同的事实：弹窗开着的时候，页签根本点不动。**
`<dialog showModal>` 把整页盖住（Playwright 报 "dialog intercepts pointer events"，
人工也点不到）。所以"弹窗里打了一半的字被切视图吞掉"**不是**今天能走到的路径 ——
今天能走到的是上面第二条（浏览器自己的前进后退不受模态限制）。草稿机制仍然按
"任何一次卸载都不许丢"来修：步骤 4 会把正文编辑器从模态里搬出来，那时这两条路会
变成同一件事。

### 4.3 丢的是什么（都是 PathView 的本地 state）

| 丢的 | 表现 | 现在住在哪 |
| --- | --- | --- |
| `dialog`、`title`、`description`、`type`、`estimate` | "新建节点"表单里**还没提交的输入** | `features/growth/drafts.ts`（模块级 Map，内存） |
| `detailNodeId`、`detailTitle`、`detailDescription`、`detailPriority`、`detailDeadline`、`detailEstimate`、`detailStart`、`detailEnd` | 详情弹窗里**改了还没保存的正文与字段** | 同上 |
| `fittedScope`（ref）→ 初始 `fitView` 再跑一次 | 用户手动平移/缩放过的视口被顶掉 | Provider 的 `viewports`（按层级，内存） |
| 时间线那一份 `viewport: { start, density }` | 切一次视图回来，时间线跳回今天 | Provider 的 `timelineViewport` |

**没有丢的**：节点位置（`positions` 在 provider 里，落 localStorage，按账户 + 空间分键）、
计划、对话 —— 正本在后端。

### 4.4 修法：为什么不删 key

原文列了两个候选（去掉 `key` 改由 effect 响应 scope 变化 / 保留 key 把编辑提到外面），
并说"等动手时再定"。实际选了后者，理由是前者要付的代价藏在细节里：`key` 同时承担着
"进入子空间时把弹窗与视口一起换掉"，直接去掉会让**弹窗跨空间残留**——而"换空间不串"
是同一批要求里明写的另一条。所以：

- `key` 留着，但换成 `canvasKey`：**哨兵值不算"换了一层"**。计划第一次到达时
  `spaceId` 会从 `'goal'` 变成真实 UUID（那一刻重建一次画布，用户什么都没做），
  而计划读失败时 `growth.goalId` 会退回哨兵值 —— 同步 `spaceId` 的那个 effect 同时加了
  这道判断，否则将来给计划加上重试之后，后端抖一下就会把用户从他正待着的子空间里弹回根。
- 没提交的输入放进模块级的草稿存储，键是 `${workspaceId}:${scopeId}`。层级 id 是 UUID
  基本不会撞，但**占位根节点的 `'goal'` 是所有空间共用的哨兵值**，少了空间这一半，
  两个还没拉到计划的空间会共享同一份草稿。
- 视口提到 Provider（按层级存）。**只活在内存，不落 localStorage**：节点集合一变，
  上一次的视口就可能框住一片空白，而"打开是一张空图"比"重新 fit 一次"更难解释。
  跨刷新那一份留给步骤 3 的 `scope_viewports`。
- 只有**用户明确关掉**（× / Esc）才丢草稿。卸载不丢 —— 卸载对用户来说什么都没发生。

>
> - **规则 5.1 那三条缺口的落点**：边不再物理删（`node_service.delete_node` 里那段硬删
>   去掉，改为只在 `mode=delete` 时执行）、恢复入口是 `POST /nodes/{id}/restore`、
>   "点之前知道代价"是 `GET /nodes/{id}/archive-impact` + 界面上那个确认框。
> - **实现时补的两处（规则里没写）**：
>   1. `archive_impact` **只读、不加工作区锁**。为画一个确认框去抢锁，会让"两个人在同一
>      秒里删不同的东西"变成其中一个人看到一句莫名其妙的等待超时。代价是这份数字可能比
>      真正执行的那一刻早几秒 —— 所以界面上的措辞是"会**带走**"，不是"已经带走"。
>   2. 恢复报告要报"哪几天超出当天上限"，就得按**和排期同一套**每日上限去算。为此把
>      `schedule_service` 里那个三档回落的 `_capacity_profile` 与墓碑状态元组改成公开名
>      （`capacity_profile` / `TOMBSTONE_SESSION_STATUSES`）复用，**没有**在恢复那一侧
>      再写一遍 —— 两处各写一份的后果是"排期说排得下、恢复报告说超了"。
> - **规则 5.3 第三条（验环）没有正常入口**：按现在的写入规则成不了环，所以那条路径只有
>   白盒用例能造出来（`test_archive_restore.py` 里那条是直接改库造的非法状态）。它验的是
>   "万一发生了，不许静默"，不是预期路径。
> - **没做到的就是 5.8 写的那些**：彻底删除只有接口、没有界面入口。这一条会一直记着。

### 5.1 一句话：现在的"删除"为什么不算归档

数据库那一层**已经是**软删除（`plan_nodes.deleted_at`），所以"改成软删除"这个说法在这
里是假的 —— 真正缺的是另外三件：

1. **它顺手把边毁了。** `node_service.delete_node` 里有一段硬删：凡是挂在被删节点上的
   `dependencies` 行一律物理删除（`node_service.py:306`）。删掉的行恢复不回来，于是"恢复"
   只能还你一个**一条前置都没有的节点** —— 而排期正是按前置算的。这不是可恢复。
2. **没有恢复入口。** 库里留着 `deleted_at`，界面上没有任何地方能看到它、点回来。
3. **点下去之前不告诉你代价。** `deletedCount` 是删完之后才回来的；那个垃圾桶按钮今天
   是**一次点击就删**（`PathView.tsx:80`），没有确认，也没有"这一下会带走几项"。

所以 3C 的实质是：**让归档真的可逆** —— 边的行留着、读路径过滤、恢复能原样回来，
并且在下手之前把影响范围说清楚。

### 5.2 节点与后代

- **归档 = 给这个节点和它当时的整棵子树盖上同一个时间戳。** 这就是现在的做法，保留：
  一次归档只有一个 `deleted_at`，于是"这一次带走的"在库里是可识别的。
- **根目标不能归档**（保留现状）：空间存在的理由就是它，删掉之后空间还在、内容全没了。
- **恢复 = 清掉"它 + 与它同一个时间戳的后代"的 `deleted_at`。** 按时间戳认人，是为了
  **不顺手复活更早以前单独归档过的节点** —— 那才是"悄悄恢复"：用户点的是这一支，
  另一支不该跟着回来。
- 恢复子树**中间**的某个节点是允许的（用户点的就是它那一行的"恢复"），但要过下面那关。

### 5.3 恢复前的三道校验（绝不悄悄恢复一个非法状态）

1. **父亲还在归档里 → 拒绝。** 一个活节点挂在归档节点下，在界面上永远不可达 ——
   用户找不到任何入口去处理它，而它真的存在。这正是现有代码注释里要避免的孤儿，
   恢复到它身上只是换了个方向制造同一件事。报 `PARENT_ARCHIVED`，并说清"先把上层
   那一支恢复出来"。
2. **彻底删除过的 → 拒绝。** 见 5.4，`purged_at` 不是空的就不给恢复，报 `NODE_PURGED`。
   少了这一条，恢复入口会把一个"彻底删除"的节点还成一条边都没有的残骸，
   而用户不会知道自己拿到的是残的。
3. **恢复后重新验环。** 把恢复进来的边并回活边集合，跑 `proposal_validation.find_cycle`；
   成环就整体回滚，报 409 + 环上的链条。**按现在的写入规则这不该发生**（归档期间两端都
   不可见，`load_node` 取不到，没人能往里加边），所以它是一道"万一发生了，不许静默"的
   断言，不是预期路径。

### 5.4 两种删除，库里必须分得开

| | `mode=archive`（**默认**） | `mode=delete` |
| --- | --- | --- |
| `deleted_at` | 打上 | 打上 |
| `purged_at` | 留空 | 打上（这就是"不可恢复"那一笔） |
| 挂在上面的边 | **行留着** | 物理删掉（就是现在这段代码） |
| 场次 | 行留着 | 行留着（历史，但不可恢复） |
| 恢复 | 可以 | 拒绝 |

`mode=delete` **仍然是软删除**：历史版本的快照里引用着这个 id（`plan_revisions.snapshot`
就是持久化的那一份），物理删行会让"V3 里这个阶段叫什么"指向空气。"彻底"指的是
**不可恢复**，不是"从历史里抹掉"。

新增的 `purged_at` 是必须的，不是顺手加的：两种删除的 `deleted_at` 一模一样，
没有这个标记，恢复入口根本分不出该不该放行。

### 5.5 关系与依赖：归档**不动行**

- 归档不碰 `dependencies`，也不碰 `node_relations`，行原样留着 —— 恢复之后图是原来的图，
  排期也不会变，还省掉一套"把边写回来"的第二次写入。
- 那为什么现在要删？`node_service.py:302` 的注释给了理由："不清就会留下指向软删除节点的
  边，投影时会被过滤掉，于是库里有、界面没有。" **这个理由今天不成立**：
  `plan_service.load_all_dependencies` 与 `load_all_node_relations` 本来就把"两端都活着"
  写进了 WHERE（各自的注释里写着同一条纪律），`schedule_service.load_schedule` 也照做。
  界面上从来就看不到那些边。那一段硬删是多余的 —— 而它恰好毁掉了恢复。
- 彻底删除时照旧物理删（现在这段代码搬过去），无所谓：那种删除本来就不给恢复。

### 5.6 排期：不动行，但要从"活计划"里摘掉

- **归档不删 `scheduled_sessions`**，但那些场次必须从活计划里消失。今天没有：
  `plan_service.load_all_sessions` 不按节点存活过滤，`build_plan` 拿
  `titles.get(session.node_id, "")` 兜住了 KeyError —— 兜不住的是"画面上多出一场没有
  名字的安排"。补上过滤。
- **容量同理。** `schedule_service` 按"空间里全部场次"算占用，归档节点的场次仍然占着
  时间池。归档该有的效果正是"这件事现在不占用我的时间"（这一句是那个文件自己写的，
  只是它当时说的是**空间**归档）。按同一个纪律补上。
- `load_today`、打卡、提醒已经按节点存活过滤了，不用改。
- **恢复不自动重排、也不丢弃**：场次跟着回来（行没动），代价是那几场可能已经过期、
  或者和归档之后新排的挤在同一天。恢复结果里如实报出来（过期几场、哪几天超出当天上限），
  界面上说清楚，让用户自己决定要不要重排。**静默重排等于替用户改计划。**

### 5.7 界面上要有的（改名字不算）

- 垃圾桶点下去**先给一份影响范围**：后代几项、关系几条、依赖几条、场次几场共多少小时。
  这份数字由后端算（前端的计划可能已经旧了），措辞是"归档"，因为它是可恢复的。
- 一个**归档列表 + 每行一个"恢复"**，能翻到"这个空间里归档过什么"。
- **恢复失败要照原话说清是哪种**：上层还在归档 / 已彻底删除 —— 这两种用户能做的事不一样。
- 恢复成功后计划要重新取，恢复出来的节点要出现在它原来的层级上。

### 5.8 这一批不做

- **不做"彻底删除"的界面入口。** 接口有、测试有、文档有，界面上只有归档 ——
  一个只在接口里存在的破坏性操作，比一个摆在按钮上的更容易回头。这一条会写进提交信息，
  当成已知缺口记着，不拿"接口支持了"当成"用户能做"。
- 不做归档的保留期与自动清理；不做恢复的撤销；不做跨空间的批量恢复。
