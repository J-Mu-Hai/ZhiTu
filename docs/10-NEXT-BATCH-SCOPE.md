## 1. 范围决定

| 项 | 决定 | 理由（一句话） |
| --- | --- | --- |
| 节点正文与关系数据持久化 | **核心优先项** | 画布上画不出线、正文刷不回来，是从"固定分类的树"走到"用户自己的分层图"的**唯一**拦路项 |
| 随笔持久化 | **明确纳入** | 界面允许"发布"，刷新后静默丢失，这是"产品在说谎"，不是"功能还没做" |

| 应用外壳 / 画布重新挂载 | **单独登记，先不修** | 它是否吞掉输入与视口，需要实测结论才好定优先级 —— 结论见下面第 4 节 |

"临时附件，刷新后失效"这句提示**在空间文件真正持久化之前必须出现在界面上**。
今天附件只是会话内的对象地址（`addFiles` 只写内存），界面上**已经有**一句
「点击选择，或拖入文件 · 仅本次会话保留」（`SpaceFiles.tsx:17`）—— 它不是没有提示，
但"仅本次会话保留"读起来更像"这个空间的资料是临时的"，而**没有把"刷新就没了"说明白**。
落库之前按更直接的那个措辞改 —— **这一句已经先改了**：`SpaceFiles.tsx` 现在写的是
「临时附件，刷新后失效」。它是持久化落地之前的占位说明，不是最终形态。

## 4. 登记问题：画布重新挂载会吞掉没保存的输入

结论先说：**会丢，而且丢的正是这一批最要紧的那些东西。** 但当前触发面很窄，所以先登记。

### 4.1 挂载点在哪

- 根布局是稳定的：`src/app/layout.tsx` 里 `AuthProvider` / `DemoProvider` / `AppShell`
  挂在模块层，路由之间不会重挂。
- `AppShell.tsx` 在 `!ready` 时返回启动屏并**不渲染 `{children}`** —— 所以页面内容是
  "从无到有"挂载一次。但 `ready` 只跟登录态恢复有关，**不受计划加载影响**。
- 真正会重复发生的是这一处：`Workbench.tsx:27` 的 `<PathView key={spaceId} />`。
  `spaceId` 由 `provider.tsx:287-289` 的 effect 在 `growth.goalId` 变化时同步，
  首次拿到计划时从 `'goal'` 变成真实 UUID → **key 变化 → 整棵 PathView 子树（含
  ReactFlow 画布）卸载重建**。

  这就是 `docs/08-DEPLOYMENT.md` 第四节记的"计划到达时整页重新挂载一次" —— 严格说不是
  "整页"，是**画布子树**：顶栏、导航在 `AppShell` 里，key 之上，它们不动。

### 4.2 什么情况会再次触发

`provider.tsx:277`：读计划失败时 `setPlan(null)`，`growth` 退回空树，`goalId` 回到 `'goal'`；
**下一次读成功又变回 UUID → 再重挂载一次**。所以不是"只在首帧发生一次"：
后端抖一下、刷新一次计划失败，用户就会看到他正在编辑的东西消失。

### 4.3 丢的是什么（都是 PathView 的本地 state，`PathView.tsx:154-182`）

| 丢的 | 表现 |
| --- | --- |
| `dialog`、`title`、`description`、`type`、`estimate` | "新建节点"表单里**还没提交的输入** |
| `detailNodeId`、`detailTitle`、`detailDescription`、`detailPriority`、`detailDeadline`、`detailEstimate`、`detailStart`、`detailEnd` | 详情弹窗里**改了还没保存的正文与字段** |
| `fittedScope`（ref） | 重置 → `PathView.tsx:305-311` 的 `fitView` 再跑一次，把用户手动平移/缩放过的视口顶掉 |

**没有丢的**：节点位置（`positions` 在 provider 里，落 localStorage，按账户 + 空间分键）、
计划、对话 —— 正本在后端。

**视口则根本没存过**，而且不止画布那一处：React Flow 的视口只活在 React Flow 内部
（没有 `/layout` 接口，也没有本地存它），时间线另有自己的一份 `viewport: { start, density }`
（`TimelineView.tsx:74`）同样只活在内存里。所以画布一重建、或者切一下视图，平移与缩放
就回到默认，画布那边只能重新 fit。这正是实施计划步骤 2 里 `scope_viewports` 要解决的东西。

### 4.4 为什么"现在不修"但"步骤 4 之前必须修"

当前能丢的只有弹窗里正在打的字，触发条件（首帧、读失败后恢复）也算窄。但这一批要做的
**正文自动保存**和**关系编辑器**，全都长在 PathView 的本地 state 上 —— 那时候重挂载吞掉的
就是"用户写了十分钟的正文"。所以它被登记为**步骤 4（正文与子空间）的前置修复项**。

不在这里拍修法。两个候选各有代价，等动手时按当时的代码再定：

- 去掉 `key={spaceId}`，改由 effect 响应 scope 变化 —— 但 key 现在同时承担"进入子空间时
  重置弹窗与视口"，直接去掉会让弹窗跨空间残留。
- 保留 key，把"未保存的编辑"提到 provider 或草稿存储里 —— 代价是更多状态提升。
