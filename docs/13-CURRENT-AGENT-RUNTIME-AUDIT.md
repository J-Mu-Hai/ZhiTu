# 知途当前智能体框架与函数能力审计

> 审计日期：2026-09-29  
> 审计基线：`33fb851`  
> 文档性质：描述**当前代码实际能做什么**，不是未来方案，也不把界面上存在的功能误算成 AI 能力。

## 0. 先给结论

当前的“智能体”准确说是：

> **一个由 openJiuwen Workflow 承载的单次结构化 LLM 调用，加上服务端上下文组装、动作校验、待确认提案和事务写入。**

它不是多 Agent，也不是会自主循环调用工具的 Agent。模型一轮中不能调用任何函数，不能在思考过程中再次查询节点、运行排期器或修改画布。它只能读服务端预先拼好的上下文，然后一次性返回：

1. 一段回复 `reply`；
2. 对规划条件的提取 `brief`；
3. 最多 80 条结构化动作 `actions`；
4. 一份分析 `analysis`。

其中只有 6 种动作能进入提案：新建节点、修改节点、归档节点、更新长笔记、新增前置依赖、删除前置依赖。动作不会立即执行，必须先通过服务端校验，再由用户整份确认后一次性写入。

所以现在的系统具备“**读一批上下文 → 给建议 → 生成一份安全提案**”的能力，但不具备“**一边访谈一边主动查资料、立即沉淀事实、逐步调用排期能力、观察结果后继续修正**”的 Agent 闭环。这是当前核心体验不顺的根因，不是单纯换提示词就能彻底解决的问题。

## 1. 总体架构

### 1.1 组件关系

```text
用户 / 前端 ConversationPanel
        │
        │ POST /api/workspaces/{workspaceId}/messages
        ▼
conversation_service.submit_turn
        │
        ├─ 校验焦点节点归属
        ├─ 保存用户消息
        ├─ build_turn_context：一次性读取上下文
        │
        ▼
Reasoner 接口
        │
        ├─ openjiuwen：生产首选
        ├─ direct：直连 DeepSeek 的备用路径
        ├─ rule：无模型时的规则兜底
        └─ script：只用于自动化测试
        │
        ▼
一次模型调用，返回 reply + brief + actions + analysis
        │
        ├─ brief_service.apply_claims：保存用户明确说出的条件
        ├─ analysis_service.record：追加 AI 分析记录
        └─ proposal_service.build_from_actions：校验并生成待确认提案
                                        │
                              用户点击“确认”
                                        │
                                        ▼
                          proposal_service.confirm_proposal
                                        │
                          加锁、校验版本、重新校验、事务写入
```

### 1.2 openJiuwen 在这里承担什么

当前 openJiuwen 的 Workflow 是一条直线：

```text
Start → LLMComponent → End
```

`LLMComponent` 使用 DeepSeek provider、系统提示词、当前回合文本和 JSON 输出声明。Workflow 中没有工具节点、路由节点、反思节点、重试规划节点或多个 Agent。每次请求都会构造这张三节点工作流，由进程级 Runner 执行。

这意味着 openJiuwen 目前主要提供的是：

- 模型客户端与 Workflow 生命周期；
- 结构化 JSON 输出；
- 对 DeepSeek 请求的统一承载；
- 模型来源与降级状态的可观测性。

它目前**没有**被用于：

- Function Calling / Tool Calling；
- 多 Agent 协作；
- ReAct 循环；
- 根据中间结果再次查库；
- 自动运行排期器；
- 长期记忆检索；
- 自动控制画布镜头。

关键实现：

- `backend/agent/runtime/openjiuwen_runtime.py`
- `backend/agent/runtime/__init__.py`
- `backend/api/dependencies/agent.py`

## 2. 一轮对话实际发生什么

入口为 `POST /api/workspaces/{workspace_id}/messages`。实际链路如下。

### 2.1 输入阶段

前端可提交：

- 用户文本；
- `clientMessageId`，用于防止重复发送重复调用模型；
- `contextNodeId`，表示当前正在讨论的节点；
- `scopeRootId`，表示本轮允许 AI 改动的子树范围；
- `currentView`，例如路径、时间线、任务或排期视图。

服务端先验证 `contextNodeId` 确实存在于当前用户的当前空间。跨用户、跨空间、不存在或已归档节点都会在读取正文、写消息和调用模型之前被拒绝。

### 2.2 幂等与消息落库

如果同一个 `clientMessageId` 已处理过，服务端直接返回之前的助手回复和提案，不再次调用模型。

新消息会先写进数据库，再调用模型。模型失败时用户消息仍然保留，接口返回 `degraded=true` 的正常响应，而不是把可预期的模型故障变成 500。

### 2.3 上下文组装

`build_turn_context` 在模型调用前一次性读取所需数据。模型调用开始之后，模型不能再主动查询更多信息。

### 2.4 单次推理

Reasoner 只暴露一个方法：

```python
reason(turn: TurnContext) -> ReasoningResult
```

生产默认配置 `AGENT_REASONER=auto`：

| 模式 | 实际行为 |
|---|---|
| `auto` | 有 key 且安装 openJiuwen 时走 openJiuwen，否则走直连；没有 key 时走规则兜底 |
| `openjiuwen` | 走 openJiuwen；SDK 不可用时记录降级并走直连 |
| `direct` | 绕过 openJiuwen，直接调用 DeepSeek |
| `rule` | 不调用模型，只根据缺失条件追问 |
| `script` | 自动化测试脚手架，回放固定 JSON，不是产品能力 |

### 2.5 模型返回后的处理

服务端在模型返回后立即检查：模型思考期间，节点、正文、结构或规划条件是否被其他请求改过。

- 如果输入变过：保留回复和历史分析，但不允许生成可确认提案；
- 如果输入没变：解析并校验动作；
- `brief` 中只有用户明确表达的条件可以进入真实规划字段；
- `analysis` 追加保存，不覆盖旧分析；
- 合法动作形成一份 `validated` 提案，仍未写入计划。

### 2.6 用户确认后的写入

用户点击确认后，服务端会：

1. 检查幂等键；
2. 锁定工作空间；
3. 比对提案基准版本与当前计划版本；
4. 用当前数据库状态重新跑一遍动作校验；
5. 在同一个事务里应用全部变更；
6. 写入计划版本快照与变更记录；
7. 整批提交。

任意一步失败，整份提案都不写入。当前不是逐条接受，而是整份接受或整份拒绝。

关键实现：

- `backend/api/routes/workspaces.py`
- `backend/services/conversation_service.py`
- `backend/services/turn_context.py`
- `backend/services/proposal_service.py`

## 3. 模型实际看得到什么

### 3.1 用户与空间信息

模型能看到：

- 当前日期、星期与时区；
- 空间标题与创建时填写的意图；
- 当前视图名称；
- 当前焦点节点；
- 当前作用范围；
- 最近 12 条历史消息；
- 当前用户消息。

它没有一套完整的用户长期画像。专业、年级、排名、经历等信息，只有在用户说过并被写进规划条件、信息节点或节点正文后，后续回合才可能继续看见。

### 3.2 规划条件

当前结构化条件包括：

- `goal`：目标；
- `deadline`：截止日期；
- `weekly_available_minutes`：每周可投入分钟数；
- `current_level`：当前水平；
- `success_criteria`：成功标准；
- `constraints`：约束条件。

其中提示词把以下三项设为“开始正式给计划前的必要条件”：

1. 截止日期；
2. 每周可投入时间；
3. 当前水平。

### 3.3 节点上下文

一次最多加载 80 个节点。模型看不到真实 UUID，只看到本轮临时句柄 `n1`、`n2`……，动作也只能引用这些句柄。

节点按五层组织：

| 层 | 含义 |
|---|---|
| `focus` | 当前正在讨论的节点 |
| `ancestor` | 焦点节点的祖先链 |
| `child` | 焦点的直属子节点 |
| `scope` | 作用范围内的其他节点 |
| `outside` | 范围外节点，可读但不可改 |

每个节点可包含：

- 标题、类型、状态、深度；
- 父节点句柄；
- `planning` 或 `information` 用途；
- 截止日期与预计工时；
- 300 字以内的简述；
- 验收标准；
- 是否存在长笔记及其字数；
- 焦点节点的长笔记正文。

长笔记上限为 20,000 码点，但只有焦点节点的长笔记正文会进入当前提示词；其他节点只告诉模型“存在一份多少字的笔记”，不会把全文送进去。

### 3.4 关系

模型能读到：

- `finish_to_start` 前置依赖；
- `related_to` 无向关联；
- `influences` 有向影响；
- 关系说明。

但是它只能写前置依赖，不能创建或修改 `related_to`、`influences`。

### 3.5 时间数据

模型能只读看到：

- 每周容量；
- 每日上限；
- 最短/最长执行场次；
- 缓冲时间；
- 周期性可用时间窗；
- 特殊日期例外；
- 已经排入日历的场次；
- 执行记录；
- 当前空间未完成任务的总工时；
- 未填写预计工时的任务数量；
- 其他活跃空间造成的占用。

这些只是上下文事实。模型不能调用排期器，也不能直接修改上述数据。

## 4. 它到底有没有“函数工具”

### 4.1 严格意义上的模型工具：0 个

当前没有向模型注册任何 Function Tool。代码里没有让模型在推理中发出 `tool_call`，也没有如下循环：

```text
模型决定调用工具 → 服务端执行 → 把结果返回模型 → 模型继续判断
```

因此它不能在同一轮主动调用：

- 读取某个节点；
- 搜索相似节点；
- 展开某个 NodeSpace；
- 查询完整关系图；
- 运行排期模拟；
- 查询冲突；
- 查找外部资料；
- 控制画布镜头；
- 创建节点后再检查结果。

### 4.2 它能输出的“动作语言”：6 种

这些动作容易被误称为“工具”，但本质上是模型最终 JSON 中的声明，模型不会得到执行结果并继续推理。

| 动作 | 模型能表达什么 | 服务端真正做什么 | 主要限制 |
|---|---|---|---|
| `create_node` | 在某个父节点下新建节点 | 形成待确认的新节点变更 | 必须有 `parentRef`；AI 新节点一定属于树结构；最多 60 个 |
| `update_node` | 修改已有节点部分字段 | 形成字段补丁并推进正文版本 | 不能改父节点，不能改用途 |
| `delete_node` | 归档节点及其整棵子树 | 确认后软删除 | 不能删除根节点；影响整棵子树 |
| `update_note` | 覆盖某节点长笔记 | 按笔记版本锁写入，来源标为 AI | 上限 20,000；是整份覆盖，不是增量编辑 |
| `create_dependency` | 创建前置 → 后续依赖 | 新增 finish-to-start 边 | 信息节点不能作为端点；不能成环 |
| `delete_dependency` | 删除前置依赖 | 删除对应依赖边 | 只能删前置依赖 |

字段限制：

- 节点标题最多 200 字；
- 简述最多 300 码点；
- 验收标准最多 1,000 字；
- 长笔记最多 20,000 码点；
- 单轮消息最多 4,000 字；
- 单轮动作最多 80 条；
- 单轮创建节点最多 60 个。

### 4.3 枚举存在、但当前明确拒绝的动作：6 种

下列名称已经存在于后端枚举中，但提案校验器当前会拒绝，模型提示词也被要求不要输出：

| 暂未开放动作 | 意图 |
|---|---|
| `schedule_sessions` | 生成具体执行场次 |
| `unschedule_sessions` | 取消执行场次 |
| `move_session` | 移动日历场次 |
| `lock_session` | 锁定场次 |
| `update_capacity` | 修改用户时间容量 |
| `update_brief` | 通过提案修改规划条件 |

规划条件目前不是通过 `update_brief` 动作写入，而是从用户自然语言中抽取 `brief claims`，再由服务端依据来源规则写入。

### 4.4 界面有、但 AI 当前完全不能操作的能力

| 能力 | 界面/后端现状 | AI 当前权限 |
|---|---|---|
| 创建独立视觉节点 | 手工双击空白可以创建 | 不可以；`create_node` 强制要求父节点 |
| 创建 `related_to` 关系 | 用户可手工创建 | 不可以 |
| 创建 `influences` 关系 | 用户可手工创建 | 不可以 |
| 修改关系说明/类型 | 用户可手工编辑 | 不可以 |
| 拖动节点与保存布局 | 用户可操作 | 不可以 |
| 移动/重新挂载父节点 | 部分手工能力可扩展 | 不可以 |
| 进入 NodeSpace | 前端导航能力 | 不可以主动控制 |
| 控制画布聚焦/缩放 | 前端能力 | 不可以 |
| 生成具体周计划/日计划 | 排期系统可预览 | 不可以直接调用排期器 |
| 调整可用时间窗 | 时间设置能力 | 不可以 |
| 完成任务/写执行记录 | 执行模块能力 | 不可以 |
| 创建或修改空间 | 空间管理能力 | 不可以 |
| 写随笔 | 随笔界面能力 | 不可以 |
| 上传/读取空间文件 | 文件能力尚不完整 | 不可以 |
| 联网研究、引用来源 | 未接入检索工具 | 不可以 |

## 5. 模型间接触发的服务端函数

下面这些不是模型可调用工具，而是服务端在固定流程中自动调用的函数。

| 阶段 | 函数/模块 | 作用 | 是否直接写计划 |
|---|---|---|---|
| 上下文 | `turn_context.build_turn_context` | 组装节点、关系、时间、历史和作用范围 | 否 |
| 推理 | `Reasoner.reason` | 执行一次模型或规则推理 | 否 |
| 条件提取 | `brief_service.apply_claims` | 保存用户明确说出的目标、时间、水平和约束 | 写规划条件，但不写节点 |
| 分析存档 | `analysis_service.record` | 追加一条 AI 分析及输入快照 | 否，不改用户正文和计划 |
| 动作解析 | `proposal_validation.validate_actions` | 校验字段、句柄、范围、重复、用途、截止日和依赖环 | 否 |
| 提案生成 | `proposal_service.build_from_actions` | 将整批合法动作存成待确认提案 | 否 |
| 用户确认 | `proposal_service.confirm_proposal` | 加锁、版本校验、重新校验、幂等处理 | 准备写入 |
| 最终执行 | `proposal_service._apply` | 新建/修改/归档节点，写笔记，增删依赖，生成版本快照 | 是，单事务 |

一个很重要的边界是：`build_from_actions` 校验失败时，一行计划数据都不会写；只有 `confirm_proposal` 内的 `_apply` 会改变计划。

## 6. 记忆与分析机制

### 6.1 对话记忆

- 对话完整记录在数据库；
- 每次提示词只携带最近 12 条消息；
- 没有向量检索；
- 没有自动摘要后的长期对话记忆；
- 没有跨空间语义记忆；
- 没有专门的用户画像记忆工具。

超过窗口的内容只有在已经沉淀到规划条件、节点、长笔记或分析记录中时，才可能继续影响后续回合。

### 6.2 AI 分析

模型可以返回：

- 已知事实；
- 未知问题；
- 证据；
- 假设；
- 诊断；
- 策略选项；
- 风险；
- 可信度说明；
- 最长 20,000 字的分析正文。

结构化栏位每栏最多 12 条、每条最多 400 字。分析使用 append-only 存储，重新分析不会覆盖旧记录。

分析的新旧状态由输入快照和当前数据比较得出，不依赖一列容易忘记更新的 `stale` 标志。如果模型思考期间输入被修改，分析可以作为“基于旧版本”的历史保留，但相应动作不会形成提案。

### 6.3 分析与行动没有自动闭环

分析记录本身不会：

- 自动创建节点；
- 自动修改正文；
- 自动转成关系；
- 自动运行排期；
- 自动安排下次追问；
- 自动聚焦画布。

只有同一份模型输出中合法的 `actions` 才可能形成提案。因此系统可能“分析得很多”，但画布完全不变化。

## 7. 安全边界与做得比较好的部分

当前架构并不是一无是处。它在安全写入方面已经相对扎实：

1. 模型看不到真实节点 UUID，只能使用当轮句柄；
2. 范围外节点服务端强制只读；
3. 所有动作使用严格判别联合，未知字段不会被静默吞掉；
4. 提案生成后不立即写计划；
5. 用户确认时再次校验，并检查计划版本；
6. 写入是事务性的，要么全部成功，要么全部失败；
7. 确认接口有幂等键，重复点击不会重复写入；
8. 笔记和节点正文各自有乐观锁版本；
9. 依赖边有环检测；
10. 信息节点不会误入排期，也不能作为依赖端点；
11. 模型调用期间数据变化时，会阻止旧动作进入提案；
12. openJiuwen、直连、规则兜底和测试脚手架的来源会如实暴露。

问题不是“写入不安全”，而是为了安全构建出的能力边界过窄，尚未补上真正的 Agent 工具闭环。

## 8. 为什么当前核心功能会不好用

### 8.1 最关键的提示词冲突：既让它记录事实，又要求条件不齐时动作必须为空

当前提示词同时写了两组规则：

- 用户说“排名 38”时，应创建 `purpose=information` 的信息节点；
- 截止时间、每周投入、当前水平三项没齐时，`actions` 必须是空数组；
- 用户只是在补充信息时，`actions` 也应为空。

这三条会相互冲突。于是访谈阶段最常见的结果就是：模型继续追问，虽然已经拿到了适合写入节点的事实，却因为“条件未齐”或“只是补充信息”而不生成动作。用户感受到的是“它听懂了，但画布没有生长”。

### 8.2 把所有目标都套进固定的三条件问卷

截止日期、每周投入和当前水平适合考试、申请、项目等目标，但并不适合所有场景。例如“探索研究方向”“整理一段经历”“理解一个问题”可能尚无截止日期。

目前规则把三项都当作正式计划开始前的硬门槛，容易产生：

- 重复追问；
- 对探索型问题过早要求日期和工时；
- 用户已经给了大量有效事实，系统仍不允许生长结构；
- 会话像填表，而不是共建。

### 8.3 它不会真正“使用系统能力”

模型虽然看到了时间容量和已排任务，但不能调用排期器。它只能修改预计工时、截止日或依赖，然后让用户另去“排期”页面预览。

所以“帮我安排这周每天做什么”无法在对话内形成真实闭环。模型可以说建议，却不能：

1. 请求一次排期模拟；
2. 读取冲突结果；
3. 调整方案；
4. 把日程差异展示给用户确认。

### 8.4 图结构能力比画布能力窄很多

画布支持树、前置、关联、影响和手工独立节点；AI 只会“父子树 + 前置依赖”。它不能建立关联/影响边，也不能创建视觉独立节点，无法表达“这个事实与多个目标有关”“这个因素影响两条路径”这类真实思考结构。

### 8.5 单次大输出代替了增量共建

模型每轮只能一次性输出最终 JSON。它不能：

- 先保存一个事实；
- 再读取更新后的画布；
- 判断是否已有相似节点；
- 运行排期模拟；
- 根据模拟结果修正计划；
- 最后只把必要差异交给用户。

因此要么没有动作，要么一次冒出一大份计划。中间缺少“边谈边长”的节奏。

### 8.6 提案只能整份确认

服务端把一轮动作当作一个原子提案。任何一条动作校验失败，整份提案不生成；用户也不能只接受其中三条、修改一条、拒绝两条。

这会放大模型的小错误：一个字段或一条边写错，整轮产出都无法落地。

### 8.7 分析层很重，行动层很轻

系统能保存九部分分析和长篇 narrative，但它们不会自动映射成画布变化、待办、时间安排或下一步操作。产品容易呈现出“AI 写了很多字”，却没有让用户的计划明显向前走。

### 8.8 上下文并不等于长期理解

最近 12 条消息、最多 80 个节点、只有焦点节点长笔记全文，足以完成局部讨论，但不足以构成持续的长期导师记忆。没有检索工具时，早期访谈信息一旦没成功落到结构化数据，后面很容易消失在窗口之外。

### 8.9 没有主动循环

当前系统只有用户发一条、模型答一条。它不会在事件发生后主动：

- 发现用户连续延期；
- 检查计划是否失衡；
- 请求缺失证据；
- 生成复盘问题；
- 提醒某个分析已过期；
- 自动提出最小修正方案。

“智能体”目前本质上仍是被动对话服务。

## 9. 当前能力边界的准确表述

### 已经做到

- 能读当前空间的一部分结构化上下文；
- 能围绕焦点节点读取祖先、直属子节点和范围信息；
- 能读取时间容量与现有排期事实；
- 能抽取用户明确说出的规划条件；
- 能保存版本化 AI 分析；
- 能生成 6 类安全、可预览、待确认的计划变更；
- 能在用户确认后原子写入并生成计划版本；
- 能在输入变化、版本冲突、越权和无效依赖时拒绝写入；
- 生产环境能够走 openJiuwen + DeepSeek，且暴露真实来源和降级状态。

### 还没有做到

- 真正的 Tool Calling；
- 多步自主规划循环；
- 边访谈边稳定生长信息节点；
- 自动决定何时保留在当前节点、何时创建子节点、何时进入 NodeSpace 的机械策略；
- AI 创建关联/影响关系；
- AI 创建视觉独立节点；
- AI 调用排期器并生成真实周计划/日计划；
- AI 修改容量、时间窗和具体场次；
- AI 控制画布视觉中心；
- 逐条编辑或部分接受提案；
- 外部资料检索与可靠引用；
- 长期语义记忆；
- 事件驱动的主动干预。

## 10. 建议的下一版：Planning Copilot v2

不建议继续只往当前大提示词里加规则。下一阶段应该保留现有的安全提案与事务写入底盘，在它前面增加真正的工具层和状态机。

### 10.1 原则

1. **读取工具可以立即执行，写入工具只生成草稿或提案。**
2. **事实采集与正式排期分成两条轨道。** 条件不齐可以阻止排期，但不能阻止信息节点生长。
3. **每次只产生最小有意义变化。** 用户回答一个关键事实，就允许出现一个小提案，不必等完整计划。
4. **排期必须由确定性服务计算，模型只设置意图、约束并解释结果。**
5. **所有高风险写入仍由用户确认。** 引入工具不等于绕过当前安全边界。

### 10.2 第一组：只读工具

建议真正注册给模型的函数：

| 工具 | 返回内容 | 解决的问题 |
|---|---|---|
| `get_scope` | 当前作用范围、焦点、可写边界 | 模型不再只依赖一段预拼文本 |
| `get_node` | 某节点简述、长笔记、版本、用途 | 需要时再读，而不是猜测未加载正文 |
| `list_children` | 某节点直属子节点 | 判断是否需要继续拆分 |
| `get_ancestors` | 目标与上层约束 | 避免局部建议偏离总目标 |
| `get_relations` | 前置、相关、影响及说明 | 让 AI 理解真正的图，而不只是树 |
| `find_similar_nodes` | 同父层或全空间相似主题 | 降低重复节点 |
| `get_time_capacity` | 容量、窗口、已占用、缺口 | 使用统一事实口径 |
| `simulate_schedule` | 确定性排期结果与冲突 | 让 AI 根据真实结果修正，而非口头猜测 |
| `get_recent_execution` | 近期完成、延期、实际耗时 | 支持复盘和滚动调整 |

### 10.3 第二组：提案工具

这些工具执行后只构造可预览差异，不直接写正式计划：

| 工具 | 应新增的能力 |
|---|---|
| `draft_create_node` | 支持树内子节点，也支持明确的独立视觉节点 |
| `draft_update_node` | 修改正文、状态、用途等受控字段 |
| `draft_move_node` | 安全地重新挂父节点并检测环 |
| `draft_relation` | 支持 dependency / related_to / influences |
| `draft_note_patch` | 支持追加、替换指定段落，避免每次整份覆盖 |
| `draft_brief_change` | 把规划条件变更放入可见提案，而不是隐藏写入 |
| `draft_schedule` | 接收排期器模拟结果并形成场次提案 |
| `draft_capacity_change` | 修改长期容量或临时时间例外 |

### 10.4 访谈状态机

建议把当前“一段大提示词”拆成明确状态：

```text
理解用户这一句话
  ↓
识别：事实 / 目标 / 约束 / 偏好 / 行动 / 证据
  ↓
立即判断落点
  ├─ 更新当前节点正文
  ├─ 创建信息节点
  ├─ 创建行动节点
  ├─ 建立关联边
  └─ 只留在对话，不入图
  ↓
判断是否需要进入子空间
  ↓
必要时调用读取工具补上下文
  ↓
条件足够时调用排期模拟
  ↓
展示本轮最小差异 + 仍需回答的最多两个问题
```

### 10.5 节点落点规则

需要把“什么时候写本节点、什么时候创建子节点、什么时候进入 NodeSpace”从纯提示词建议升级为服务端可测试策略。

建议规则：

- 一句话只是补充当前主题的解释或证据：写当前节点简述/长笔记；
- 可独立命名、以后会被反复引用的事实：创建 `information` 子节点；
- 有完成状态、产出、工时或截止日：创建 `planning` 节点；
- 一个主题出现至少两个稳定子方向，或需要独立关系图/时间线：允许把该节点展开为 NodeSpace；
- 与多个分支有关但不从属于任何一个：创建独立视觉节点并用 `related_to` / `influences` 连接；
- 只是临时聊天、情绪表达或尚未确认的猜测：留在对话或分析，不进入用户事实层。

### 10.6 修复优先级

建议按以下顺序推进：

#### P0：先让访谈真的共建

1. 删除“条件不齐时所有 actions 必须为空”的总闸；
2. 改为“条件不齐时禁止生成完整排期，但允许保存信息节点、正文和关系”；
3. 为一条用户回答生成小型可确认提案；
4. 增加稳定测试：排名、经历、限制等回答必须有可见落点；
5. 给提案增加逐条接受或至少按分组接受。

#### P1：接通图与排期

1. 增加 `related_to` / `influences` 提案动作；
2. 增加独立视觉节点语义；
3. 接入 `simulate_schedule` 只读工具；
4. 增加排期场次提案；
5. 允许 AI 根据真实冲突重新调整计划。

#### P2：形成持续智能

1. 对话摘要与长期检索；
2. 执行偏差事件触发；
3. 过期分析主动提示；
4. 画布镜头协议；
5. 依据不同目标类型选择不同访谈模板，而不是所有场景统一三问。

## 11. 验收下一版不能只看“模型会不会说”

建议建立以下产品级验收：

1. 用户说“我排名 38/40”后，本轮必须出现信息落点，不允许只追问；
2. 用户连续回答三条背景信息，画布应逐步生长，而不是第三轮后一次性冒出全部；
3. 探索型目标没有截止日期时，系统仍能整理主题结构；
4. 用户说“每周只有 6 小时”后，容量进入结构化条件，并能调用排期模拟；
5. 排期冲突时，AI 必须引用模拟结果，不能凭空说“排得开”；
6. 用户说两个主题互相影响时，AI 能提出 `influences`，而不是强行塞成父子关系；
7. AI 需要未加载正文时，应调用读取工具，不能把“没读到”当“没有”；
8. 用户只接受一部分建议时，剩余建议不应阻止已接受部分落地；
9. 每一项 AI 写入都能追溯来源、版本与用户确认；
10. 相同访谈脚本重复运行多次，关键事实落点和规划骨架应达到稳定阈值，而不是只验一次成功。

## 13. 最终判断

当前版本已经有一个可靠的“AI 提案安全底盘”，但还没有达到用户通常理解的“规划智能体”。

它目前最适合被称为：

> **带版本保护和用户确认的结构化规划助手。**

要变成真正好用的规划智能体，下一步重点不应是继续增加回答文字、分析栏目或提示词规则，而应是：

> **把读取、图谱、排期与最小变更做成模型能够分步调用、能够观察结果、但仍受提案确认保护的工具。**

其中第一优先级是拆掉“条件不齐就完全不生长”的总闸，让访谈得到的有效事实从第一轮开始就有稳定、可见、可确认的落点。
