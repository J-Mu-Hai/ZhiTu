# 规划智能体重构设计 V1：先想清楚，再排出来，最后做起来

## 1. 文档目的

本设计替代“用户输入目标后立即生成路线、问题节点或周计划”的交互。它定义一个以**目标判断**为起点、以**可确认时间架构**为中点、以**周计划和重规划**为终点的规划智能体。

它不是让模型自行管理全部流程，也不是把用户带进一长串问卷。程序负责阶段、数据边界、确认与版本安全；AI 负责提出判断、筛选关键因素、解释取舍，并在恰当时机邀请用户讨论。

本设计的核心原则是：

> 先判断目标是否正确，再理解结果由什么决定，再决定怎样走，最后决定何时做与本周做什么。

## 2. 用户可见的三阶段与内部五层

界面始终只显示三个容易理解的阶段，避免把内部推理流程变成用户的学习负担。

| 用户看到的阶段 | 内部完成的层 | 该阶段的完成标志 |
| --- | --- | --- |
| 想清楚 | 重新确认目标 → 分析影响因素 → 形成战略路径 → 粗粒度时间架构 | 用户看到并确认一条“先后顺序 + 阶段范围 + 关键成果”的粗时间线 |
| 排出来 | 将粗时间架构落到具体日期、月/周、里程碑、依赖与缓冲 | 用户确认正式时间线 |
| 做起来 | 当前周计划 → 日计划 → 执行反馈 → 对未来重规划 | 每周有可执行计划，偏差会形成一份可确认的未来调整方案 |

内部的五层绝不能越级：没有明确战略前不排每天任务；没有正式时间线前不写执行计划；历史发生后不允许被重规划静默改写。

```text
原始目标
  → 目标重构
  → 因素模型
  → 战略路径
  → 粗时间架构
  → 详细时间线
  → 当前周 / 日计划
  → 反馈与未来重规划
```

## 3. 总体验：创建空间后的第一分钟

### 3.1 创建目标空间

用户输入“学习 Python”“准备保研”或“做一个 AI 产品”并创建空间后，不应立即出现一堆待回答卡片，也不应直接生成课程/任务列表。

右侧对话区切为“初步思考”模式：

- 输入框放大、居中，提示用户补充“为什么是现在、希望得到什么、最担心什么”；
- 画布只显示根目标与三组折叠的思考框架，不生成任务节点；
- AI 首次回复先给 2–4 句整体判断：它识别到的目标假设、潜在歧义和此刻最重要的决策；
- AI 只抛出**一个**最能改变路线的关键问题，不将问题清单倾倒到对话框。

示例：用户输入“我想学 Python”。

> Python 本身不是结果，它可能服务于自动化、数据分析、AI 项目或求职。四条路线的最小成果不同，所以我先不排课程。你希望在学习结束时，能拿出什么具体结果证明它解决了你的问题？

### 3.2 画布不是问卷

进入空间时，系统可立即建立固定的分析节点，但这些节点是**待验证的思考容器**，不是待用户逐项填写的表单：

- 节点展示 AI 当前判断、已知事实、未知点和“为什么这件事重要”；
- 用户点击任一节点，右侧进入该节点的局部讨论；
- 局部讨论可补充信息、选择 AI 给出的备选判断，或反驳它；
- AI 只在确实需要用户决定时提出一个关联该节点的问题；
- 未选择节点时，对话保持全局视角，不展示十几个问题卡。

## 4. 阶段一「想清楚」：三层分析与粗时间架构

阶段一不是计划阶段。其产物是经用户确认的目标定义、问题模型、战略路径和粗时间架构；其中不创建正式任务、日程或可执行 `PlanNode`。

### 4.1 层 A：重新确认目标

根目标下建立一个“目标重构”分组，含五个固定节点。首次创建的是 AI 的暂定判断，节点状态可为 `待讨论 / 已澄清 / 暂缓 / 不适用`。

| 节点 | 标识 | AI 可以写什么 | AI 不可以做什么 |
| --- | --- | --- | --- |
| 你现在在哪 | `current_state` | 已有能力、资源、环境、现实限制，以及依据不足处 | 把“Python 水平”单项问题当成完整现状 |
| 你真正想要什么 | `true_intent` | 表面目标背后可能的成果、动机和使用场景 | 把推测当作用户事实，或替用户定义人生目标 |
| 这件事值得做吗 | `value_assessment` | 目标与长期方向的关系、替代路径、投入产出与伪目标风险 | 给出命令式人生判断或假装掌握用户未提供的处境 |
| 真正卡你的是什么 | `key_conflict` | 1–2 个最有杠杆的矛盾、为什么它比其他问题重要 | 罗列十个泛泛困难，或过早询问工具/课程/每日安排 |
| 最后到底要做到什么 | `goal_definition` | 可观察的成果定义、能力边界、成功判据和暂定时间窗 | 未经用户确认把定义写成正式目标 |

体验示例：

用户点击“你真正想要什么”。右侧不弹出长表单，而显示：

> 我目前有三个解释：做出 AI 小项目、获得实习所需能力、减少对他人代码的依赖。它们会导向不同的学习深度。哪一个最接近你现在的真实诉求？

用户的答案只更新该节点及受影响节点；不会重新生成整张地图或把答案自动写成计划。

### 4.2 层 B：分析影响因素

当目标定义达到“足以讨论”的置信度后，系统展开“问题结构”分组。这里的五类因素同样是推理节点，不是任务。

| 节点 | 标识 | 应产出的结论 |
| --- | --- | --- |
| 硬约束 | `hard_constraints` | 不可随意改变的政策、截止窗口、设备、时间、资格或规则 |
| 可控变量 | `controllable_factors` | 用户可以通过行动改变的 3–8 个变量 |
| 关键杠杆 | `key_levers` | 最可能改变最终结果的 1–3 个变量及理由 |
| 主要风险 | `major_risks` | 最可能让战略失败的风险、早期信号和缓冲办法 |
| 外部条件 | `external_conditions` | 政策、竞争、导师、市场、公开信息等非个人因素 |

AI 的任务不是收集“尽可能多的信息”，而是从候选因素中筛出 5–8 个高影响因素。筛选标准应可解释：影响结果的程度、不可逆性、时间敏感性、信息不确定性和可控性。

对于可以公开验证的事实，允许由研究工具取得来源；研究结果只能成为证据，不得把检索结论伪装成用户事实或替代用户价值选择。

### 4.3 层 C：形成战略路径

当目标和因素模型足够稳定，AI 在“战略路径”分组生成一个可讨论的战略草案。它至少说明：

- 主线：最优先投入什么；
- 增量线：可以并行、但不应挤占主线的行动；
- 放弃或暂缓：当前不值得做什么；
- 依赖关系：哪些动作必须先后发生；
- 风险控制：何处设置检查点或备用路径；
- 战略取舍：为什么选择此路线而不是另一路线。

此处的路径是“行动逻辑”，不是日历。它可以是“先补最小能力闭环，再做可展示成果”，但不能写成“周一看课程、周二刷题”。

### 4.4 阶段一的完成产物：粗时间架构

阶段一的最后一步，是把已讨论的战略路径投影为 3–6 个阶段的**粗时间架构**。这是“想清楚”结束的唯一标志。

每个阶段只包含：

- 阶段名称；
- 相对范围（如第 1–2 周、约 1 个月）或已知的日期范围；
- 阶段目标；
- 可验证成果；
- 完成标准；
- 与前后阶段的依赖关系。

没有截止日期时，系统以相对周为真值，给出合理区间，不因缺日期阻塞。这个架构是草案，用户选择“确认进入详细排期”后才进入阶段二。

## 5. 阶段二「排出来」：一条正式时间线

阶段二只解决时间关系，不再反复讨论“目标是不是对的”。如果用户改变了目标或关键约束，系统提示回到受影响的思考节点，并生成重算草案。

### 5.1 时间线体验

- 页面核心是唯一的主时间轴；阶段显示为轴内的区间条，终点是里程碑点；
- 有明确截止日期时，使用真实开始/结束日期、月和周；
- 没有截止日期时，使用第 1 周、第 2 周等相对周，不伪造日历日期；
- 点击区间条打开侧栏，查看目标、核心动作、成果、完成标准、依赖与风险；
- 用户可调整阶段顺序、范围或缓冲，AI 解释影响而不静默改写；
- 旧的“轴上方策略卡片”不再作为时间线的主要呈现。

### 5.2 详细时间线的结构

每个正式阶段应有：

```text
阶段 ID / 标题
开始和结束（真实日期或相对周）
战略目标
关键动作（不是每日任务）
可交付成果
验收标准
前置依赖与风险缓冲
状态：草案 / 已确认 / 进行中 / 已完成 / 已调整
```

用户确认时间线后，才允许把阶段写为正式计划对象。写入必须继续沿用：

```text
proposal → 用户确认 → 版本校验 → 事务写入
```

## 6. 阶段三「做起来」：周计划、日计划与自动重规划

### 6.1 当前周体验

正式时间线确认后，系统只展开：

- 当前周计划；
- 下一周预览；
- 当前周内的具体日计划。

日计划不是将所有任务均摊到七天。AI 应根据阶段目标、任务依赖、用户可用时间和风险缓冲，给出少量可执行的工作块；用户可调整，再通过提案确认落地。

每项任务都必须可追溯：

```text
根目标 → 战略路径 → 时间线阶段 → 周计划 → 日计划 / 任务
```

### 6.2 周末回顾与重规划

每个周末或用户主动结束本周时，系统自动发起“回顾入口”，而不是静默重写计划：

1. 汇总完成度、未完成原因、实际投入与阻塞点；
2. 判断偏差是否影响后续阶段；
3. 若需要调整，生成重规划草案；
4. 向用户展示“保留什么、归档什么、未来如何后移/换路线”；
5. 用户确认后，原子更新未来计划。

自动化只意味着“自动分析并准备草案”，不意味着自动改变用户已确认的计划。

重规划规则：

- 已完成任务、历史反馈、已完成阶段绝不改写；
- 只替换当前和未来的未完成工作；
- 旧周计划及未完成任务以可恢复历史版本保留；
- 新版本必须是唯一活跃版本；
- 原因与替换关系可追溯。

## 7. 画布信息架构与交互约束

### 7.1 层级布局

画布必须反映逻辑层次，而不是平铺所有节点：

```text
根目标
 ├─ 目标重构
 │   ├─ 当前状态 / 真实意图 / 价值评估 / 核心矛盾 / 目标定义
 ├─ 问题结构
 │   ├─ 硬约束 / 可控变量 / 关键杠杆 / 主要风险 / 外部条件
 └─ 战略路径
     ├─ 主线 / 增量线 / 暂缓项 / 风险控制
         └─ 粗时间架构（3–6 个阶段）
```

分组默认折叠。主画布默认只显示根目标、三个分组和当前焦点，避免首次进入就出现散乱的十几个卡片。展开分组后，自动使用稳定的层级布局；用户手工拖动的位置应保留。

### 7.2 节点内容规范

每个分析节点卡片只展示：标题、当前判断的一句话摘要、状态和证据/讨论数量。完整内容在右侧节点讨论中呈现。

节点详情必须区分：

- 已知事实（来自用户、公开来源或系统记录）；
- AI 假设；
- 当前判断及理由；
- 尚需确认的一件事；
- 可能的下一步。

不显示模型隐藏思维链，不把“AI 内部思考”伪装成事实。

## 8. 状态机与写入边界

建议的内部状态如下：

```text
INITIAL_THINKING
  → GOAL_REFRAME
  → FACTOR_ANALYSIS
  → STRATEGY_DRAFT
  → COARSE_TIMELINE_REVIEW
  → DETAILED_TIMELINE_DRAFT
  → WEEKLY_EXECUTION
  ↔ WEEKLY_REVIEW / REPLANNING
```

状态切换由程序控制，模型只能提交符合当前阶段 schema 的“建议内容”。

| 阶段 | 允许写入 | 禁止写入 |
| --- | --- | --- |
| 初步思考、目标重构、因素分析、战略草案 | reasoning nodes、节点讨论、可审阅结论、证据 | 正式阶段、月/周/日任务、排期 |
| 粗时间架构审阅 | 时间线草案 | 未经确认的正式计划节点 |
| 详细时间线 | 待确认阶段/里程碑 proposal | 自动正式写入 |
| 周计划与重规划 | 经确认的周/日计划与可恢复历史版本 | 修改已完成历史、静默替换未来 |

## 9. AI 行为规范：避免“人机式问卷”

1. 每次先给判断，再问一个问题；不以“请提供 A/B/C/D”开场。
2. 只问会改变战略、阶段顺序、时间范围或成果定义的问题。
3. 工具、课程、IDE、具体资料、每天几点等执行细节，最早在阶段三讨论。
4. 已知信息不得重复问；公开可验证信息优先通过研究工具核对，并显式标注来源状态。
5. 问题不足以影响决策时，AI 应做合理暂定并说明“可在后续调整”，而不是无限追问。
6. 每次最多存在一个需要回答的全局问题；局部问题只在用户主动打开对应节点后出现。
7. 模型失效、校验拒绝或等待外部信息时，UI 必须给出明确状态和重试入口，不能只停在“正在处理”。

## 10. 端到端体验验收脚本

以“我想在 30 天内学 Python，并做一个能展示的数据分析小项目”为例：

1. 用户创建空间，看到放大的“初步思考”输入区；
2. AI 判断这更像“用项目建立可展示能力”，而非单纯学语法，并询问成果定义；
3. 画布出现三组折叠框架；用户进入“当前状态”和“核心矛盾”补充信息；
4. AI 生成并解释目标定义、关键杠杆和战略路径；
5. AI 生成“基础闭环 → 最小分析项目 → 展示与复盘”的粗时间架构；用户确认；
6. 系统切换至时间线，将三阶段渲染为 30 天内的真实区间与里程碑；用户确认正式排期；
7. 系统只生成本周计划、下周预览和本周的日计划；
8. 周末用户反馈只完成 40%；系统展示偏差影响与重规划草案；
9. 用户确认后，旧未完成计划归档，未来阶段及新周/日计划更新，已完成历史不变。

若以上九步有任一步需要用户手动猜“下一步在哪里”、看见一堆无关问题，或看到未经确认即写入的任务，则体验不合格。

## 11. 分期实施建议

为避免再次把稳定闭环和认知重构混在一起，建议按以下顺序实施：

1. **P1：阶段一画布与节点讨论。** 建立三组层级、15 个固定分析容器、初步思考输入区、节点局部讨论；不改时间线写入。
2. **P2：目标/因素/战略内容生成。** 将模板从“直接输出问题与路线”改为“模型生成可校验的判断、假设、证据和一个关键问题”；保留状态机。
3. **P3：粗时间架构到详细时间线的转换。** 明确两类时间对象与确认边界，复用现有时间线主轴。
4. **P4：周计划、日计划和周末自动回顾。** 保留当前版本化重规划语义，增加日计划与自动发起回顾入口。

每一阶段都应保持已有 `proposal → 用户确认 → 版本校验 → transaction` 边界；不得用“更聪明的模型”绕过数据安全和用户确认。
